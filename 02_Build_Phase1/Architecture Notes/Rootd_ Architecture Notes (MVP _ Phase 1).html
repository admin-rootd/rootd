Rootd: Architecture Notes (MVP / Phase 1)

Status: v0.2, approved, 7 Oct 2026. Owner: Ace (IT lead). Scope: Phase 1 web app, Standalone (PR/Citizenship) first, then Full Pathway (NLV/DNV). Mobile comes later.

Working assumptions: development is local only (no hosting yet), and "Rootd" is a working name, not final.

1. Guiding principles

  1. The rules decide, the AI drafts. Eligibility results come only from the deterministic, versioned rules engine. AI only generates editable document drafts.
  2. Rules are data a lawyer can read. Rules live in versioned files, separate from UI code, so legal review has one source of truth.
  3. Minimise personal data. Passports, income and criminal records are high-risk. Collect, store and send to third parties as little as possible.
  4. EU-first. All data processing is in EU regions, with DPAs signed with every processor.
  5. One language, one codebase. TypeScript everywhere, so web and mobile share the rules and types.

4. System overview

  • Web (Next.js) renders the free eligibility checker, results, paywall, document editor and stage tracker. Server Actions / Route Handlers do all privileged work.
  • Rules package is called server-side for authoritative results and may also run client-side for instant UI feedback. The server result is the one that counts and is stored.
  • Supabase holds users, intake answers, eligibility results (with rule-set version), document drafts, stage state and purchases.
  • AI wrapper takes structured, minimised inputs plus a versioned template, and returns a draft the user can edit. Output is always labelled as a template, not legal advice.
  • Stripe handles checkout and tax. Webhooks update the entitlement table, and the app trusts only the webhook, never the client.

5. Rules engine

  • Each rule set is versioned (nlv-dnv@1.0.0). Every stored result records the version used.
  • Rules are declarative (thresholds, conditions, consulate mapping) and the evaluator is small and pure.
  • Full Pathway and Standalone are separate packages with no shared logic. Standalone reports present vs missing only, never valid vs invalid.
  • Golden test suite (Vitest): a table of input profiles with expected outcomes, reviewed and signed off by the attorney. Changing a rule requires updating and re-approving the cases.
  • Changes to rule files go through PR review with a mandatory legal-review checklist item.

6. Data protection and retention

  • Anonymous first: the free checker needs no signup. Answers stay in the browser session and only persist after the user creates an account.
  • Uploaded documents (deferred, not in current scope): when built, stored in a private Supabase Storage bucket, encrypted at rest, accessed only via short-lived signed URLs and RLS policies. Auto-delete after a set period. Proposed default: 30 days after last activity, configurable, to be confirmed with the lawyer. Implemented with a scheduled job (pg_cron) that removes files and records.
  • Extra protection for the most sensitive items (e.g. criminal record certificates): application-level encryption before upload, with keys held outside the database. Decide before building the upload feature.
  • AI minimisation: send only the fields a template needs, redact identifiers (passport and NIE/NIF numbers) where they aren't required, and use a provider with a signed DPA and no training on inputs.
  • Logging: no PII in logs, error reports or analytics events.
  • User rights: build export and delete-my-account from the start, not as an afterthought.

8. Mobile path (later)

  • Expo app in apps/mobile reuses rules, schemas, doc-templates and the API layer. Only UI is rewritten.
  • Payments caveat: Apple and Google require their in-app purchase systems for digital goods sold inside apps (with commission). Options: sell on web only and let the app sign in to unlock, or add in-app purchases later. Decide before the mobile phase, since it affects pricing.

9. Local development setup

  • Run Supabase locally with supabase start (Docker): local Postgres, Auth and Storage, with migrations in supabase/migrations.
  • Next.js runs with pnpm dev through Turborepo. Stripe is not needed yet (see the payments reminder).
  • Real data on a local machine: Standalone testing will use real people's PII. Keep it out of the repo (.gitignore, no seed files with real data), use full-disk encryption, use synthetic data for automated tests, and don't paste real data into tickets, chats or AI prompts. Get testers' consent in writing, even friends.

10. Phase 1 build plan: Standalone first

Standalone has to build the foundations itself (data model, PII handling, rules skeleton), so the 6-8 week estimate from the checklist (which assumed Full Pathway's foundations) becomes about 8-10 weeks part-time. Full Pathway follows and reuses the foundations.

Track 2: Full Pathway, NLV / DNV (after Track 1): about 12 weeks, as in the checklist, reusing the data model and checklist patterns. Includes the Stripe paywall.

11. Open points

  1. Document uploads: deferred. When picked up, decide the retention period (30 days proposed, confirm with the lawyer), whether users upload at all or self-confirm each step, and application-level encryption for the most sensitive items.
  2. Standalone pricing model (undecided in the spec).
  3. Which AI provider to start with behind the wrapper, and the regions its DPA covers.
  4. Final app name (see reminders).

12. Reminders

  • Mobile payments: Apple and Google require their in-app purchase systems for digital goods sold inside apps, with commission. Options are web-only purchase with sign-in in the app, or in-app purchases. Decide before the mobile phase, since it affects pricing.
  • Company entity and jurisdiction: decide with a lawyer or accountant. It affects the Stripe account, VAT and the data processing agreements.
  • Name: once the name is final, check trademark and domain availability before branding work goes far.
  • Legal gates (from the checklist): the Standalone review is its own scoped pass, with a higher bar than Full Pathway. Co-founder agreements go in writing before shared production code.
